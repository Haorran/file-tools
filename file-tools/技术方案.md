> 版本：v1.0
> 更新日期：2026-07-15
> 产品中文名：文件查重
> 产品英文名：File Check

---

## 一、分段策略

### 选择：按功能分段

**理由：**

1. **功能独立性强**：「目录比较」和「目录内查重」是两个完全独立的功能模块，共享底层算法（局部哈希、SHA256、容量格式化），但业务流程无交叉。按功能分段可让每段自包含、可独立测试。
2. **风险前置**：核心 shell 脚本是整个应用的业务根基，先实现并充分验证脚本逻辑，再包装 Web 层，可避免「UI 做完了但后端逻辑有 bug」的返工。
3. **符合飞牛 FPK 开发流程**：先确定核心运行文件 → 再搭建 Web 服务 → 最后组装 FPK 包，每段产出物清晰。

### 分段总览

| 阶段 | 内容 | 产出物 |
|------|------|--------|
| 第一段 | 核心 shell 脚本开发 | `dir_compare_check.sh`、`dir_duplicate_check.sh` |
| 第二段 | Web 后端服务（Node.js） | Express 服务，封装脚本调用为 REST API + SSE 流式输出 |
| 第三段 | Web 前端 UI | React 页面，提供参数配置、任务触发、实时进度与结果展示 |
| 第四段 | FPK 应用打包 | manifest、cmd 脚本、config 配置、入口配置、`.fpk` 文件 |

## 二、第一段：核心 Shell 脚本开发

### 2.1 做什么

开发两个独立的 Bash 脚本，实现产品规格文档中定义的全部校验逻辑：

- `dir_compare_check.sh` — 目录比较
- `dir_duplicate_check.sh` — 目录内查重

### 2.2 涉及的模块/组件

| 模块 | 文件 | 说明 |
|------|------|------|
| 目录比较脚本 | `app/scripts/dir_compare_check.sh` | 三步骤流程：清单比对 → 内容校验 → 容量统计 |
| 目录内查重脚本 | `app/scripts/dir_duplicate_check.sh` | 三步骤流程：生成清单 → 计算标识分组 → 输出重复组 |
| 共享工具函数 | `app/scripts/lib/common.sh` | 可读容量格式化、局部哈希计算、临时文件管理、进度输出 |

### 2.3 共享工具函数 `common.sh`

```bash
# 提供以下函数：
# - format_bytes()        # 字节数 → 可读格式（B/KB/MB/GB）
# - partial_hash()        # 计算文件首尾64KB局部哈希，输出 {head}_{tail}
# - full_sha256()         # 计算全文件SHA256
# - progress()            # 输出进度到 stderr：进度 [当前/总数] 名称
# - setup_cleanup()       # trap 注册 EXIT/INT/TERM 信号自动清理临时文件
# - create_temp()         # mktemp 包装，自动纳入清理列表
```

### 2.4 `dir_compare_check.sh` 设计

**输入：** `dir_compare_check.sh <模式0|1|2> <目录A> <目录B>`

**流程：**

```
参数校验
  ├── 检查参数数量 == 3
  ├── 检查模式值 ∈ {0,1,2}
  ├── 检查目录A、目录B存在且为目录
  └── 失败 → exit 1/2

步骤1 — 文件清单比对（所有模式）
  ├── find 目录A → 排序 → 生成相对路径清单 → 临时文件 tmpA
  ├── find 目录B → 排序 → 生成相对路径清单 → 临时文件 tmpB
  ├── comm -23 tmpA tmpB → 仅A存在文件列表
  ├── comm -13 tmpA tmpB → 仅B存在文件列表
  ├── comm -12 tmpA tmpB → 共有文件列表 → tmpCommon
  └── 输出差异清单

步骤2 — 内容校验（模式0跳过）
  ├── 遍历 tmpCommon 中每个文件
  ├── 先比较文件大小（stat -c%s）
  ├── 模式1/2：计算首尾64KB局部哈希比较
  ├── 模式2：额外计算全文件SHA256比较
  ├── 进度输出到 stderr
  └── 记录不一致文件

步骤3 — 容量统计（所有模式）
  ├── 遍历目录A全部文件 → 文件数 + 总字节
  ├── 遍历目录B全部文件 → 文件数 + 总字节
  ├── 输出容量汇总表
  └── 比对文件数和字节数

最终结论
  ├── 无任何差异 → exit 0
  └── 有差异 → exit 99
```

**退出码：** 0（通过）、1（参数错误）、2（目录不存在）、99（校验失败）

### 2.5 `dir_duplicate_check.sh` 设计

**输入：** `dir_duplicate_check.sh <模式0|1|2> <扫描目录> [过滤阈值KB]`

**流程：**

```
参数校验
  ├── 检查参数数量 ∈ {2,3}
  ├── 检查模式值 ∈ {0,1,2}
  ├── 检查扫描目录存在
  ├── 若有阈值参数，检查为纯数字
  └── 失败 → exit 1/2

步骤1 — 生成文件清单
  ├── find 扫描目录 → 递归所有普通文件 → 临时文件 tmpList
  ├── 统计文件总数
  └── 输出总数

步骤2 — 计算校验标识并分组
  ├── 遍历 tmpList 中每个文件
  ├── 若有过滤阈值且文件大小 < 阈值 → 跳过（计数）
  ├── 根据模式计算 key：
  │   ├── 模式0：key = basename
  │   ├── 模式1：key = size_head64kHash_tail64kHash
  │   └── 模式2：key = full_sha256
  ├── 写入缓存：key \t size \t filepath → tmpCache
  └── 进度输出到 stderr

步骤3 — 分组匹配并输出
  ├── sort tmpCache | awk 按key聚合
  ├── 筛选文件数 >= 2 的分组
  ├── 输出每组：校验标识、文件大小、文件路径列表
  └── 输出统计汇总（分组数、冗余文件数、可释放空间）

退出
  └── exit 0（无论是否发现重复）
```

**退出码：** 0（完成）、1（参数错误）、2（目录不存在）

### 2.6 输入

| 脚本 | 输入 |
|------|------|
| dir_compare_check.sh | 命令行参数：模式、目录A、目录B |
| dir_duplicate_check.sh | 命令行参数：模式、扫描目录、可选阈值 |

### 2.7 输出

| 脚本 | 输出 |
|------|------|
| dir_compare_check.sh | stdout：差异清单、内容不一致详情、容量汇总表、最终结论 |
| dir_duplicate_check.sh | stdout：重复文件分组、统计汇总 |
| 两者 | stderr：实时进度信息 |

## 三、第二段：Web 后端服务（Node.js）

### 3.1 做什么

搭建 Node.js Express 服务，将两个 shell 脚本封装为 REST API，通过 SSE（Server-Sent Events）实现前端实时获取进度和结果。

### 3.2 涉及的模块/组件

| 模块 | 文件 | 说明 |
|------|------|------|
| 入口 | `app/server/server.js` | Express 应用，监听 Unix Socket |
| 路由-目录比较 | `app/server/routes/compare.js` | POST /api/compare — 启动目录比较任务 |
| 路由-目录查重 | `app/server/routes/duplicate.js` | POST /api/duplicate — 启动目录内查重任务 |
| 路由-SSE | `app/server/routes/events.js` | GET /api/events/:taskId — SSE 流式推送进度和结果 |
| 脚本执行器 | `app/server/lib/runner.js` | 封装 child_process.spawn，捕获 stdout/stderr，分发事件 |
| 前端静态文件 | `app/server/public/` | 构建后的前端产物 |

### 3.3 API 设计

#### POST /api/compare — 启动目录比较

**请求体：**
```json
{
  "mode": 1,
  "dirA": "/vol1/backup/movies",
  "dirB": "/vol2/backup/movies"
}
```

**响应：**
```json
{
  "taskId": "abc123",
  "sseUrl": "/app/file-check/api/events/abc123"
}
```

#### POST /api/duplicate — 启动目录内查重

**请求体：**
```json
{
  "mode": 1,
  "scanDir": "/vol1/media",
  "filterKB": 1024
}
```

**响应：**
```json
{
  "taskId": "def456",
  "sseUrl": "/app/file-check/api/events/def456"
}
```

#### GET /api/events/:taskId — SSE 事件流

**事件类型：**

| event | data | 说明 |
|-------|------|------|
| `progress` | `{ current, total, name }` | 实时进度 |
| `stdout` | `{ line }` | 脚本标准输出行 |
| `stderr` | `{ line }` | 脚本标准错误行（进度信息） |
| `exit` | `{ code }` | 脚本退出，code 为退出码 |
| `error` | `{ message }` | 执行异常 |

### 3.4 脚本执行器 `runner.js` 设计

```
class TaskRunner {
  tasks: Map<taskId, ChildProcess>

  createTask(scriptPath, args) → taskId
    ├── 生成唯一 taskId
    ├── spawn("bash", [scriptPath, ...args])
    ├── 捕获 stdout → 逐行分发 'stdout' 事件
    ├── 捕获 stderr → 逐行分发 'stderr' 事件
    ├── 进程退出 → 分发 'exit' 事件
    └── 存入 tasks Map

  getTask(taskId) → ChildProcess | null
  removeTask(taskId)
}
```

### 3.5 路径安全

- 所有传入的目录路径必须为绝对路径
- 拒绝包含 `..` 的路径
- 验证目录存在性（在 spawn 前检查）
- 脚本路径使用 `path.resolve(__dirname, '../scripts/')` 拼接，不接受外部输入

### 3.6 输入

| 来源 | 输入 |
|------|------|
| HTTP 请求 | JSON body：mode、dirA/dirB/scanDir、filterKB |
| 环境变量 | TRIM_APPDEST、TRIM_DATA_SHARE_PATHS（定位脚本和数据目录） |

### 3.7 输出

| 产出 | 说明 |
|------|------|
| HTTP 响应 | taskId 和 SSE URL |
| SSE 事件流 | 进度、输出行、退出码 |
| 日志 | 应用日志写入 `${TRIM_PKGVAR}/app.log` |


### 5.6 cmd/main 设计

```bash
#!/bin/bash

LOG_FILE="${TRIM_PKGVAR}/app.log"
PID_FILE="${TRIM_PKGVAR}/app.pid"

export PATH=/var/apps/nodejs_v22/target/bin:$PATH

APP_DIR="${TRIM_APPDEST}/server"
SOCKET_PATH="${TRIM_APPDEST}/app.sock"
GATEWAY_PREFIX="/app/file-check"

log_msg() {
  echo "$(date '+%Y-%m-%d %H:%M:%S') - $1" >> "$LOG_FILE"
}

check_process() {
  local pid="$1"
  kill -0 "$pid" 2>/dev/null
}

status_app() {
  if [ -f "$PID_FILE" ]; then
    local pid
    pid="$(head -n 1 "$PID_FILE" | tr -d '[:space:]')"
    if [ -n "$pid" ] && check_process "$pid"; then
      return 0
    fi
    rm -f "$PID_FILE"
  fi
  return 1
}

start_app() {
  if status_app; then
    return 0
  fi
  log_msg "Starting File Check..."
  cd "$APP_DIR" || exit 1
  GATEWAY_PREFIX="$GATEWAY_PREFIX" SOCKET_PATH="$SOCKET_PATH" \
    node server.js >> "$LOG_FILE" 2>&1 &
  echo "$!" > "$PID_FILE"
}

stop_app() {
  log_msg "Stopping File Check..."
  if [ ! -f "$PID_FILE" ]; then
    return 0
  fi
  local pid
  pid="$(head -n 1 "$PID_FILE" | tr -d '[:space:]')"
  if [ -z "$pid" ] || ! check_process "$pid"; then
    rm -f "$PID_FILE"
    return 0
  fi
  kill -TERM "$pid" 2>> "$LOG_FILE" || true
  local count=0
  while check_process "$pid" && [ "$count" -lt 10 ]; do
    sleep 1
    count=$((count + 1))
  done
  if check_process "$pid"; then
    kill -KILL "$pid" 2>> "$LOG_FILE" || true
  fi
  rm -f "$PID_FILE"
  rm -f "$SOCKET_PATH"
}

case "$1" in
  start)   start_app ;;
  stop)    stop_app ;;
  status)  status_app && exit 0 || exit 3 ;;
  *)       echo "Unknown command: $1" > "$TRIM_TEMP_LOGFILE"; exit 1 ;;
esac
```

## 七、关键技术决策

### 7.1 为什么选择统一网关而非端口服务

| 维度 | 统一网关 | 端口服务 |
|------|---------|----------|
| 访问域名 | 复用飞牛系统域名 | 需要单独端口 |
| 登录态 | 自动校验 NAS 登录态 | 需自行处理认证 |
| 用户身份 | 通过 Header 转发 X-Trim-Userid | 无内置用户上下文 |
| 安全性 | 网关层拦截未登录请求 | 端口暴露在局域网 |

文件查重涉及用户文件访问，需要可靠的用户身份识别和登录态校验，统一网关是更合适的选择。

### 7.2 为什么用 SSE 而非 WebSocket

| 维度 | SSE | WebSocket |
|------|-----|----------|
| 方向 | 单向（服务端 → 客户端）| 双向 |
| 复杂度 | 低，原生 EventSource API | 需要额外库 |
| 断线重连 | 浏览器自动重连 | 需手动实现 |
| 适配网关 | 统一网关原生支持 | 统一网关支持 |

文件查重的任务进度推送是典型的单向推送场景，SSE 足够且更简单。

### 7.3 为什么脚本和 Web 服务分离

- **shell 脚本独立可用**：用户也可以直接在终端运行脚本，不依赖 Web 服务
- **职责清晰**：脚本负责核心计算逻辑，Web 服务负责 HTTP 接口和并发管理
- **可测试性**：脚本可以单独测试，不依赖 Node.js 环境
- **复用性**：共享的 `common.sh` 工具函数可被两个脚本复用

### 7.4 并发任务管理

- 使用内存 Map 存储活跃任务（taskId → ChildProcess）
- 每个任务独立子进程，互不干扰
- 任务完成后自动清理进程引用
- 建议限制最大并发任务数（如 5 个），防止资源耗尽
- 服务重启后所有运行中的任务终止（可接受，用户重新发起即可）

## 八、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 大目录扫描耗时过长 | 用户体验差 | 实时进度反馈；模式 0 快速预检；过滤阈值跳过小文件 |
| 内存占用过高 | 服务崩溃 | 流式处理文件列表，不一次性加载到内存 |
| 磁盘空间不足 | 临时文件写入失败 | 脚本开头检查可用空间；使用 mktemp 创建临时文件 |
| 脚本执行超时 | 前端长时间等待 | 设置合理超时（如 2 小时）；超时后自动终止并提示 |
| 权限不足 | 脚本无法读取目标文件 | 通过应用设置引导用户授权目录 |
| Node.js 运行时未安装 | 服务无法启动 | install_init 检查运行时；缺失时写入 TRIM_TEMP_LOGFILE 报错 |
